## 2. 项目概述

### 2.1 任务说明

本项目面向两个动态交互图开展时序链接预测。每条测试查询包含一个源节点、一个时间戳
以及100个候选目标节点；提交结果需要为每个候选节点赋予一个分数，评测指标为基于留出
真实目标节点计算的 MRR。因果边界受到严格约束：任何特征均不得读取晚于当前待评分查询
时间的交互信息。

### 2.2 两类场景

两个数据集在结构上存在明显差异，该差异并非基于先验假设，而是直接从原始文件中
实测得到；可通过以下命令查看：

`python main.py --dataset <name> --stage preprocess`

| 属性 | 数据集1 | 数据集2 |
|---|---|---|
| 图结构 | 非二部图（源节点角色与目标节点角色存在重叠） | 二部图（源节点角色与目标节点角色无重叠） |
| 测试查询数 | 61,051 | 153,420 |
| 每条查询的候选数 | 100 | 100 |
| 提交成员文件 | `dataset1.csv`，61,051 × 100 | `dataset2.csv`，153,420 × 100 |

由于两个图的结构不同，两条处理链共享嵌入训练阶段和学习型排序阶段，但在后续处理上
有所分化：数据集1采用历史感知排序和两个确定性后处理器；数据集2采用同事件组反馈排序、
矩阵分解几何信息、等值 CRF 以及最终的跨时间解码器。

### 2.3 方案概述

1. **表示学习。** 每个数据集均使用 Jittor 训练两类嵌入模型：联合训练一阶目标和
   二阶目标的 LINE 模型，以及采用与节点度成比例的负采样方式进行贝叶斯个性化排序的
   BPR-MF 模型。每类模型均训练两次：一次使用完整训练历史，另一次使用在固定时间切点
   截断后的历史，从而使排序器能够基于符合因果约束的历史回放进行训练。
2. **学习型排序。** 使用 LightGBM LambdaRank 模型，基于人工构建的特征对候选节点
   进行评分。特征包括协同过滤、基于嵌入相似度的 item-CF、流行度动态、交互历史及
   嵌入点积等。训练时，特征历史冻结在时间切点；推理时，特征历史冻结在训练数据的
   结束时刻。需要向未来外推的时间特征会被裁剪至训练阶段观测到的取值范围内。
3. **结构化后处理。** 排序完成后，应用根据数据生成机制的实测不变量推导出的确定性
   规则。这些规则不是学习得到的，也不存在利用测试数据拟合的自由参数。
4. **最终序列化。** 在写出任何成员文件之前，强制输出门禁会检查矩阵形状、数值有限性
   以及取值是否位于 `[0, 1]` 区间。

### 2.4 主要创新点

* **对 LambdaRank 边际分数逐行执行最小—最大值序列化。** LambdaRank 输出的是无界
  原始边际分数，数值可能跨越零点，而提交格式要求所有数值位于 `[0, 1]`。处理链对
  每一行执行最小—最大值归一化。该变换严格保持行内排序，因此不会影响 MRR；但它是
  整条处理链中的关键步骤，因为数据集1的两个后处理器及输出门禁均以单位区间为前提。
* **基于结构不变量的后处理。** 多项规则利用了训练数据中实测得到、而非主观假设的
  不变量。例如，在数据集2训练数据的2,264,807个“源节点—目标节点”对中，没有任何
  一对在两个不同时间戳重复出现。因此，对于同一源节点而言，某一跨时间查询中的已标注
  答案可以作为其他时间查询中的负例。
* **同事件组反馈。** 数据集2中有大量测试行共享同一个 `(source, time)` 事件。三轮
  排序器会将同一事件内其他查询的预测结果反馈为后续轮次的特征。
* **基于矩阵分解的同组几何信息。** 第二轮和第三轮中的同组信息通过对 split-0
  源节点—目标节点矩阵执行秩为128的截断 SVD 进行传递。
* **基于行序的等值 CRF。** 数据集2原始测试文件的行序保留了跨源节点的同时间、
  同答案连续结构；处理链通过相邻行上的链式 CRF 利用该耦合关系。
* **阶段完成契约。** 该项属于工程创新而非建模创新，但它是确保复现结果可信的关键；
  详见第3.4节。

## 3. 规范架构

### 3.1 仅使用 Jittor

正式处理链**仅使用 Jittor**。所有神经网络训练均通过 `src/train_line_jt.py`
和 `src/train_bpr_jt.py` 完成。正式入口不提供后端命令行选项，不使用后端环境变量，
也不存在回退路径。对提交代码树执行静态导入闭包分析后，可达的第三方依赖仅包括
`jittor`、`lightgbm`、`numpy`、`pandas`、`scipy` 和 `tqdm`；PyTorch 在该闭包中
不可达，复现环境不安装 PyTorch，两个环境配置文件中也均未声明 PyTorch。

项目版本历史中保留了两个训练器的历史 PyTorch 实现，但这些代码**不包含在本次
提交包中**。比赛明确要求使用 Jittor，若同时提交第二套后端，会造成“究竟哪套代码
生成了评测结果”的不必要歧义。

### 3.2 与框架无关的共享组件

`src/pipeline_common.py` 负责运行目录契约、数据根目录契约以及共享数据工具，包括
历史索引、共现统计、相似用户缓存和逐行归一化等。该模块既不导入 Jittor，也不导入
PyTorch。这一设计是有意为之：排序阶段可以使用其中的公共工具，而不会间接引入深度
学习框架；同时，产物生产者和消费者使用同一个函数推导产物路径，避免双方对产物位置
产生不一致理解。

### 3.3 Jittor 承担的计算

模型参数、损失函数和优化器均由 Jittor 管理。两个训练器中的采样、数据打乱和负样本
拒绝均由设置了随机种子的 NumPy 执行。这样既可以缩小与深度学习框架相关的代码范围、
提高跨版本稳健性，也可以使采样序列独立于具体框架而保持可复现。

### 3.4 阶段完成契约

处理链中的每个阶段均写出一个产物，并在产物旁写出一个完成记录：

`<output>.done.json`

只有当该完成记录能够证明阶段已正确完成时，该阶段才会被视为**已经完成**。完成记录
包含：

- 产出该产物的 Git 提交；
- 该阶段所依赖的精确源文件摘要；
- 每个输入文件的大小及 SHA256；
- 科学配置摘要；
- 随机种子；
- 请求训练轮数和实际完成轮数；
- 输出文件自身的大小及 SHA256；
- 阶段专属验证结果。

完成记录是最后发布的文件：程序在执行 `fsync` 后，通过原子重命名发布该记录。因此，
完成记录存在即意味着对应产物已经通过验证。任何不匹配情况——包括缺少完成记录、
输入发生变化、Git 提交不同、配置不同、训练轮数不足或存在遗留的部分文件——都会使
运行过程**停止并输出诊断信息**。程序不会仅因输出文件存在而跳过某个阶段，也不会
静默删除或修复任何文件。

该机制对复现尤为重要。神经网络训练器会在训练过程中周期性导出嵌入，因此中断的训练
可能留下一个外观上类似完整导出结果的文件。按照阶段完成契约，该文件没有完成记录，
后续运行将拒绝使用它。

### 4.3 训练与推理逻辑

**两个数据集通用的时间截断划分协议。** 学习型排序器不能使用测试标签训练，因此采用
近期历史回放方式构建训练数据：固定时间切点之前的交互构成特征历史（split 0），切点
之后的交互提供正样本（split 1）。对于每个正样本，负样本从测试文件为该源节点提供的
候选池中抽取，使训练查询与测试查询具有相同结构。计算特征时，全部历史信息均冻结在
时间切点。

推理阶段使用完全相同的特征代码，但历史冻结时刻改为训练数据的结束时刻，并在真实测试
候选上计算。两个需要向未来外推的时间特征会被裁剪到训练阶段观测到的取值范围，从而
避免模型接收到超出训练分布支持范围的取值。

**嵌入训练。** LINE 在双向真实边上训练，对一阶节点对表和二阶节点—上下文表使用联合
目标：

`loss1 + 0.5 * loss2`

负样本通过针对已观测边集合的拒绝采样得到。BPR-MF 使用以下目标训练：

`-log sigmoid(e_src . e_dst - e_src . e_neg)`

负采样分布为节点度的0.75次幂。

### 5.2 必需的 Jittor 运行时设置

```bash
export conv_opt=1
export use_mkl=0
```

上述设置**并非性能调优选项**，而是当前镜像中正常运行所必需的配置。Jittor 1.3.10
会按名称加载 cuDNN 8 的组件库（如 `libcudnn_ops_infer.so` 等），而 cuDNN 9 已将这些
组件合并至 `libcudnn.so.9`；设置 `conv_opt=1` 后，Jittor 将使用当前能够正常解析的
cuBLAS 路径。设置 `use_mkl=0` 则可避免调用在该主机上无法正常退出的 DNNL 验证程序。

上述行为已在目标主机上直接验证：未设置两个变量时，Jittor 冒烟测试会**异常终止**
（退出码134，提示 `terminate called without an active exception`）；设置后，相同
测试可以通过，包括启用 CUDA、识别 `sm_89`、执行矩阵乘法、自动求导及一次 Adam
优化步骤。

正式入口会将这两个变量应用于其启动的所有阶段，在运行开始时打印其值，并将其记录在
每个完成记录中。如果外部环境已将任一变量设置为冲突值，程序将直接**停止运行**，而
不会静默覆盖外部设置。

## 6. 官方数据目录结构

提交压缩包中**不包含任何比赛数据**。程序预期的数据目录结构如下：

```
<data-root>/
\-- data_A/
    +-- dataset1/
    |   +-- train.csv        列：src, dst, time
    |   \-- test.csv         列：src, time, c1 … c100
    \-- dataset2/
        +-- train.csv
        \-- test.csv
```

默认 `<data-root>` 为 `code/data`；可使用 `--data-root` 将运行过程指向其他位置。
除阶段自身生成的产物外，任何阶段均不会读取该根目录之外的文件。

**任何位置均未使用测试集标签真值。** 本代码无法获得测试标签，训练协议也不需要测试
标签：排序器通过训练数据的时间截断回放进行训练。**处理链不会使用冻结预测作为计算

- 阶段以非零状态退出；
- 生成了不完整产物；
- 产物未通过验证；
- 实际完成的训练轮数少于请求轮数。

## 9. 最终提交文件的生成方式

1. 排序器首先写出基础分数矩阵：每条测试查询对应一行，每行100个数值，格式为
   `%.6f`。该文件是**中间产物**，并非正式提交文件。
2. 数据集1：`build_ds1_member.py` 按固定顺序应用两个冻结的后处理器，并写出
   `dataset1.csv`。
3. 数据集2：`crf_promote.py` 应用 CRF 及不变量降权，随后
   `build_ds2_member.py` 应用跨时间互斥解码，并写出 `dataset2.csv`。
4. 在序列化任何字节之前，`validate_submission_matrix` 会检查矩阵形状是否符合预期、
   所有数值是否有限，以及所有数值是否位于 `[0, 1]`。**该函数只报告问题并终止，
   绝不会执行截断修正。** 成员文件未通过该门禁，说明其上游处理链存在问题；若静默
   修复数值，将破坏诊断证据并改变候选排序。
5. 序列化完成后，程序还会检查文件结构，包括总行数和每行字段数，以发现仅靠内存矩阵
   检查无法识别的截断写入或不规则行。
6. 数据集2解码器具有**字节保持性**：它会直接交换基础成员文件原始字节中的两个受影响
   分数*字符串单元*，而不是重新序列化15,342,000个浮点数。因此，所有未受影响的单元格
   均与基础文件生成的字节完全一致。随后程序还会验证，字符串交换路径与浮点数路径在
   每一行的候选排序上完全一致。
7. 最终 A 榜压缩包根目录仅包含 `dataset1.csv` 和 `dataset2.csv` 两个文件。

## 11. 可复现性与非确定性

* 两个数据集的“原始数据到最终成员文件”处理链，均已在目标环境中基于官方原始数据
  各自完成一次完整的 Jittor 执行。这两次运行构成本次提交的科学证据。
* 规范入口与阶段完成契约已在同一目标环境上，针对真实 Jittor 训练阶段单独完成验证。
* 发布候选版本还接受了下游环节与整洁提交包的集成验证：将提交包解压至空目录后，
  **仅依据该解压副本**运行了真实的 LightGBM 排序器、真实的矩阵分解几何计算、真实的
  特征缓存契约、真实的 CRF，以及两个真实的成员文件构建程序（输入为符合生产数据模式
  的有界测试数据），并对生成的两个成员文件执行了最终输出闸门校验。
* **未执行第二次完整的双数据集重跑。** 这是主动决定：重复已有证据支持的训练过程，
  并不能验证上述各项验证尚未覆盖的任何内容。
* **不同独立运行之间的 GPU 训练不保证字节级确定性。** Jittor 在 GPU 上的内核调度
  无法保证逐比特复现，同时原始 A 榜运行时的模型状态也未被保留。
* 因此，**重新训练得到的成员文件可能与历史 A 榜成员文件并非字节级一致**。一次干净
  的数据集1复现结果与历史成员文件的实测对比为：Top-1 一致率95.60%，逐行 Spearman
  相关系数均值0.873。这是重新训练处理链的正常表现，并非程序缺陷。
* **本文不声明复现结果与隐藏榜分数等价。** 由于无法获得测试标签，因此无法离线判断
  新复现结果的实际榜单分数，本文也不作此类声明。
* 采样、数据打乱和负样本拒绝均由设定随机种子的 NumPy 执行，其可复现性独立于深度
  学习框架。
* 完成记录可以防止另一类错误：静默复用由不同 Git 提交、不同输入或不同配置生成的
  过期产物，并将其错误地作为本次复现结果。

## 12. 已知问题及注意事项

1. **已移除“文件存在即跳过”的行为。** 早期运行脚本只要发现输出文件存在，就会将
   对应阶段视为完成。规范处理链已不允许该行为；复用阶段必须具有有效完成记录。
2. **历史1.92 GiB数据集2特征缓存不可复用。** 该缓存生成于阶段完成契约建立之前，
   没有对应完成记录，因此数据集2运行时需要重新构建该缓存，耗时约2.8小时。程序不会
   在缺乏可信来源的情况下直接采纳该缓存，因为为来源不明的产物补写完成记录会破坏
   阶段完成契约的意义。
3. **行结束符。** 数据集1的*中间排序器 CSV* 使用平台默认行结束符：Linux 使用 LF，
   Windows 使用 CRLF。解析后的数值不受影响，最终成员文件也不受影响，因为最终写出
   程序明确固定使用 CRLF。跨平台差异仅存在于中间文件的字节表示。
4. **JittorGeometric 已安装并锁定版本，但生产处理链不直接导入该库**，详见第3.5节。
5. **文档所述 Jittor 运行时设置为必需配置，而非可选配置。** 未设置 `conv_opt=1`
   和 `use_mkl=0` 时，当前镜像中的 Jittor 冒烟测试会异常终止，详见第5.2节。
6. **无 PyTorch 依赖。** 规范提交包不包含 Torch 导入，环境中也不安装 Torch。
7. **入口中的两个阶段在提交包中仅用于信息展示。** `--stage describe` 和
   `--stage package --verify` 会读取指向已验收 A 榜压缩包的哈希锚点。由于该压缩包
   不允许重新分发，因此不会包含在本次提交材料中。复现过程不依赖上述两个阶段；
   `--stage run` 可以独立完成运行。
8. **从解压后的提交包内产生的完成记录，其 `producing_commit` 字段为 `"UNKNOWN"`。**
   提交包按设计不包含 `.git` 目录，因此无法读取提交哈希。该行为是刻意设计且失败安全
   的：`"UNKNOWN"` 不会与任何真实提交哈希相等，因此包内写出的记录不会与在 Git 检出中
   写出的记录相互误认，反之亦然。完成记录绑定的其他身份信息——各输入的哈希、配置摘要、
   相关代码摘要、输出哈希、轮次计数——均不受影响，且仍然强制校验。
9. **`--output-root` 路由在全链路中均正确，数据集2各阶段同样如此。** 所有生产方与
   消费方均通过共享路径契约（`pipeline_common.line_run_dir`、`bpr_run_dir`、
   `outputs_root`）解析各自的运行目录，因此写入指定产物根目录的产物只会从该根目录被
   读取，不会从其他位置读取。此前有两个数据集2消费方将目录写成字面量、从而忽略该选项；
   该问题已于2026-08-02由定向验证发现并修正。在默认产物根目录下，修正后的表达式解析
   结果与原字面量逐字节一致，因此不会遗留任何已有产物；
   `tests/strategies/test_ds2_output_root_contract.py` 以行为测试固定了默认路径一致性、
   隔离根目录路由，以及默认目录中存在过期产物时的行为。
